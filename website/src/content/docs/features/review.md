title: 评审与清理

---

## /review

让 agent 评审 git 改动并输出按严重度排序的发现清单,只读,不改任何文件。不带参数弹出四选一的预设菜单:

| 预设 | 说明 |
|---|---|
| 对比基准分支 | PR 式,再选一个分支 |
| 未提交变更 | 工作树里的改动 |
| 审查某个提交 | 再从最近提交列表里挑一个 |
| 自定义审查说明 | 补充关注点后评审未提交变更 |

也可直打:

```
/review uncommitted
/review base main
/review commit <sha>
/review custom 重点看并发安全
```

评审以一轮对话呈现,之后可直接追问。运行中打 `/review` 不会被拒,而是排队等当前链条结束。服务端只把 git 摘要与可直接运行的命令嵌进提示词,不嵌完整 diff,agent 自己按需读。

`/review` 是一个扩展(`src/extensions/review/`),命令、预设、二级选择器都在扩展里;它复用核心的 git 收集器。

## /simplify

对齐 Claude Code:审查变更代码的清理机会并**直接应用修复**,保持未提交,留给你检查。两阶段编排:

1. 四个**并行只读 explore 子代理**各领一个维度(复用仓库里已有的实现、化简冗余逻辑、效率、抽象层级),各自独立上下文与步数预算,只报告不动手。
2. 主对话跑一轮应用轮,汇总去重、对照当前工作区核实,直接应用修复。

正确性 bug 不在这一轮的职责内,那是 `/review` 的事。裸命令默认清理未提交改动;也可沿用 `/review` 的范围语法(`/simplify base main`、`/simplify commit <sha>`、`/simplify custom <焦点>`),或传一个路径或焦点作为清理目标(`/simplify src/foo.ts`)。

第一阶段期间主 agent 空闲但视为忙碌:`esc` 被忽略,提交的消息被拒绝,等应用轮开始后再插话。失败的维度保留位置并标注「未覆盖」,全部失败仍会跑应用轮。
