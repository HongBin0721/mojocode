# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`mojocode` — a terminal coding agent (full-screen OpenTUI TUI + headless `-p` mode) that works with any LLM via the Vercel AI SDK (Kimi / DeepSeek / GLM presets + any OpenAI-compatible endpoint). ESM-only, TypeScript with `strict` and `noUncheckedIndexedAccess`. **Single process, Pi-style**: TUI, agent core, tools, extensions, MCP, LSP and the session store all live in one process (the opencode-style `serve` sidecar, the REST+SSE protocol and the Electron GUI were removed on purpose — see the process-model paragraph below). Runtime split: `-p`/subcommands run on Node ≥ 22; the TUI needs native FFI — Bun (primary, single-binary distribution) or Node ≥ 26.1 with `--experimental-ffi` (auto re-exec injects the flag, see `src/app/runtime.ts`).

**Code comments and the README are written in Simplified Chinese** — keep new comments in Chinese to match.

There is no lint config; `npm run typecheck` is the correctness gate alongside tests — and since it is the only gate, the root tsconfig turns on `noUnusedLocals`/`noUnusedParameters`: a refactor that moves a feature out leaves dead imports and stale references behind, and without those flags nothing catches them (the extension extraction shipped four such files past a green typecheck). UI tests need Bun because OpenTUI's test renderer is the real native renderer (FFI); `vitest.ui.config.ts` forces the `bun` export condition and the `bun --bun` prefix forces the Bun runtime (plain `bunx vitest` silently runs Node via the shebang).

Solid JSX cannot be compiled by esbuild — both build lanes run `babel-preset-solid` with `{ moduleName: '@opentui/solid', generate: 'universal' }`: tsup via `esbuild-plugin-solid`, vitest (both configs) via the shared inline plugin in `vitest.solid.ts` (deliberately NOT vite-plugin-solid: it injects jsdom + a `browser` resolve condition that crashes Bun fork workers at boot). **The `solid-js` server-stub trap**: bare `solid-js` resolves to `dist/server.js` (a non-reactive SSR stub — onMount/createEffect are no-ops, so keyboard subscriptions silently die and the first frame looks fine) under Node's `node` condition AND Bun's `worker` condition. Fixes are load-bearing in three places: tsup's `renderChunk` rewrites emitted `"solid-js"` specifiers to `"solid-js/dist/solid.js"`, tsup `noExternal: ['@opentui/solid']` freezes the node variant (which pre-pins the client build) into the TUI chunk (the bun variant imports bare solid-js and relies on an upstream Bun loader plugin we don't ship), and vitest aliases both `solid-js` and `@opentui/solid` to the same pinned files. Single-instance matters: two solid-js copies = signals in one, effects in the other, updates never tracked.

## Architecture

Core principle: **the agent core never imports the UI framework (SolidJS).** `src/core/events.ts` defines the contract — the core emits typed `AgentEvent`s over a minimal `EventBus`. The same agent loop therefore drives both the OpenTUI TUI (`src/ui/App.tsx`) and the non-interactive `-p` renderer (`src/app/headless.ts`). The UI consumes the narrow `SessionHandle` interface (`src/app/session-handle.ts`); the `Session` from bootstrap satisfies it structurally, and UI tests build fake sessions against it (`tests/support/extensions.ts`'s `stubExtensions()` must list every extension-facing member App reads — a missing one crashes App at mount).

**Process model (Pi-style single process).** The TUI runs the agent core in its own process: `cli.tsx` bootstraps a `Session` and hands it straight to `runTui`; `-p` does the same with `renderHeadless`. This used to be an opencode-style client-server split (managed `serve --managed` sidecar, REST + SSE, `--attach`, plus an Electron GUI as a second client); it was removed deliberately when the user chose Pi's extension model over the GUI — extensions can now hand the TUI a **component** (`ctx.ui.custom`, `setWidget`, tool `renderCall`/`renderResult`), which no wire could carry. Consequences: there is no protocol layer, no `StateSnapshot`, no RPC serialization, no reconnect/replay buffer; `Session` methods are called directly, so "instant vs deferred" no longer exists; session reads like `extensionCommands`/`uiRequests` are plain getters and change notification is the `extensionsChanged` listener; a crash in an extension/MCP/LSP takes the TUI down with it (there is no sidecar to outlive), which is why bootstrap turns every extension failure into a startup notice and hooks never let handler errors bubble. Startup notices (`Session.startupNotices`) still exist because bootstrap emits before anyone subscribes to the bus: headless drains them after `bus.on`, App drains them on mount. Do not reintroduce a server "for later": `--attach`/remote is a different product decision, not a missing feature.

Wiring happens in `src/app/bootstrap.ts`: it builds the `Session` object (agent + bus + tools + extensions + session store) that the TUI and headless consume; `setReasoningEffort`/`doctor` are Session methods (not direct field pokes from the UI) so the UI and the extension API (`setThinkingLevel`) share one path and the hooks fire from it. **扩展的装配也在这里**：一份 `extensionTools`（name → 工厂）与 `extensionRuntime`（key → 运行时快照 getter），`registerTool` 对主 agent 的 `tools` 是**就地改键**（与运行中的 Agent 共享引用，下一次开流生效，syncSkillTool 同款），子 agent 的工具集每次现建、直接从表里现算，由工厂按 `ToolScope` 自己决定给不给（explore 不给 MCP）。内置工具名有一张 `BUILTIN_TOOL_NAMES` 黑名单，扩展注册它们直接抛错——一个装错的扩展不该把 `read` 顶掉。**工具搬进扩展时必须同时把它从这张黑名单里删掉**：曾有一个工具随扩展搬走后名字留在表里，于是那个扩展一 `registerTool` 就撞上自己，`serve` 进程启动即 exit 1、TUI 报「无法启动 mojocode server」。当时全套测试是绿的——每个扩展都拿 `fakeExtensionApi` 单测，没有一处把「真 bootstrap × 真 BUILTIN_EXTENSIONS」这条装配线跑通过，而 `node dist/cli.js --version` 根本不建会话。`tests/bootstrap-extensions.test.ts` 就是补这个洞的：真 bootstrap 一次（独立 HOME）、装全部一方扩展、断言公开可观察的接线（命令表、`disabledExtensions` 生效）。它断言不到「扩展工具真的挂上了」——`Agent` 没有公开的工具集读口，而那件事由 bootstrap 不抛异常兜住，正是上述崩溃的形态；不为一条测试新开公开面。**它也走不到 commander 那一层**：一个 flag 在 `cli.tsx` 里被顺手删掉，全套测试照样绿——bootstrap 的测试都直接调 `bootstrap()`，没有一处从 commander 走起。改 CLI 选项时用 `node dist/cli.js --help` 冒烟一遍。`todo` 是扩展工具，「子 agent 不给」由它的工厂按 `ToolScope` 自己判，不在 bootstrap 里剔。`BootstrapOptions.disabledExtensions` 按 id 跳过加载（一方与磁盘扩展都认），`--no-mcp` 走的就是这条路（`skipMcp` 随之退役）：功能搬成扩展之后，「关掉一个功能」天然就是「不加载那个扩展」。**磁盘扩展的装载也在这里**（`src/extensions/loader.ts` + `packages.ts`，Pi `.mojocode/packages` 先于全局；它可能带技能，`SkillManager` 要在建好之前拿到目录），配置里记着却不在盘上的包只出一条 startup notice；磁盘扩展装不上（模块形状不对、setup 抛错、id 撞车）**一律变成 startup notice 然后跳过**，一方扩展装不上则照常抛——那是我们自己的 bug，该在 CI 里红。模块形状是 Pi 的 `export default (api) => {…}`（或 `{ id?, setup }`；id 缺省从文件名推，`foo/index.ts` → `foo`，包里的冠以 `<包名>/`），`Extension.setup` 因此允许 async。TypeScript 扩展在 Bun 上原生 import，Node 上按需 `import('jiti')` 转译（与 Pi 相同；jiti 是运行时依赖，只在真有磁盘扩展时才加载，单二进制走的是 Bun 那条路）。**jiti 实例是进程级单例**，不是每个文件一份：每个实例带自己的模块注册表，逐文件新建会让每个扩展把 zod/ai 这类共享依赖各自重新解析求值一遍（实测三个各 import zod 的扩展：逐文件 106ms，共享一份 15ms）。配置 `packages` 在层合并时**取并集**（`--local` 装的不该顶掉全局的），且是 `configSchema` 与 `partialConfigSchema` 都要写的带默认值字段。`tests/extension-loader.test.ts` 跑的是真 bootstrap × 四个来源（含一个坏扩展与一个不在盘上的包），两条 CI lane 各考一条加载路；`tests/packages.test.ts` 用注入的 runner 断言 npm/git 的 argv，不联网。`remove` **不看 scope**：两个 base 与两层配置都清（`configured` 本来就是合并后的，用户不必记得当初加没加 `--local`；只按一个 scope 清会「报成功但什么都没做」），而且只有那一层真的记着这条 spec 时才回写——否则会凭空给项目建一个只含空 `packages` 的配置文件。`discoverExtensions` **不抛**、返回 `{extensions, notFound}`：一个 `-e` 打错字不该把前面几个来源已经发现的扩展一起丢掉；`notFound` 里是**路径而不是成句的英文**，文案由调用方本地化（这一层也在无会话的 CLI 路径上跑），与 `ReviewFailure` → `FAILURE_NOTICES` 同一条分工。四类来源与每个目录项都是并发探的，顺序在收集后按装载优先级拼回来。 `src/cli.tsx` is the commander entry point (subcommands: `auth`, `models`, `providers`, `sessions`, `config`, `doctor`, `install`, `remove`, `extensions`). **The TUI is a lazy `import('./ui/tui.js')` behind `loadTuiOrExplain()`** — never import `src/ui/` (→ kit → `@opentui/core`, which needs FFI at module load) statically from `cli.tsx` or anything on the `-p` path; tsup `splitting: true` keeps the TUI in its own chunk so `dist/cli.js` stays FFI-free.

`src/app/doctor.ts` powers both `mojocode doctor` and the TUI's `/doctor`: `collectDoctor()` gathers levelled checks (env / config / provider / search / MCP / sessions / workspace) into a `DoctorReport`, `formatDoctor()` renders it. Check `id`s are the stable contract for `--json` and tests; `label`/`detail` are localized. A `fail` check sets exit code 1. Two things to keep in mind when touching it: commander lets the *root* command swallow `-C` and `--json` when a subcommand declares the same names, so the doctor action reads them off `program.opts()`; and the TUI passes `session.config` plus the mcp extension's published runtime statuses into `runDoctor()` so the report reflects in-session `/model` changes and does **not** re-connect MCP servers (that would spawn a second child process per stdio server). `runtimeOf` returning `undefined` is ambiguous by construction — either nobody published that key, or the publisher had nothing to report — so bootstrap passes `mcpOff` alongside, derived from `extensionRuntime.has(MCP_RUNTIME_KEY)`: under `--no-mcp` nobody publishes, and without the flag doctor read that as "this session checked nothing" and connected every configured stdio server itself, spawning exactly the children this invariant forbids. LSP needs no such flag — its getter returns `undefined` even when the extension is loaded (the manager is lazy), so both readings mean "go probe".

Data flow for one turn: `Agent.run()` (`src/agent/loop.ts`, wraps AI SDK `streamText` with `stepCountIs`) → events stream to the renderer → `onHistoryChange` persists history to an append-only JSONL in `~/.mojocode/sessions/` via `SessionStore` (incremental `append` records when the array is a pure extension of what was last saved — reference-prefix compare — otherwise a full `snapshot`; a `<id>.meta.json` sidecar makes `list()` O(1) per session; session-level state — changed files — rides along as `state` records; 扩展自己的状态(todo 清单、`/goal` 的条件)走 `custom` 记录). The store keeps **two histories**: `messages` (model-facing; compaction replaces the prefix with a summary) and `displayMessages` (never shrunk by compaction — `/resume` replays it so the user sees the original conversation; rewind is a real deletion and trims both). Snapshot records carry a `display` field only when the two differ; legacy files without it are reconstructed by shape (`reconcileDisplay`), and both are exposed on `StoreHandle`.

**扩展钩子层(Pi 式,`src/core/hooks.ts`)。** 功能从核心搬出去成为扩展靠的是这一层,不是 bus:bus 是同步、单向、给渲染层看的事实流,处理器返回值无意义;钩子异步、按注册顺序串行、返回值有意义。命名用 snake_case(`before_agent_start` / `tool_call` / `tool_result` / `turn_start` / `turn_end` / `agent_end`)与 bus 的 kebab-case 区分。每个输入带 `subagent` 标记——子 agent(task / fork 技能)与主 agent 共享同一份 `HookRegistry`(bootstrap 建一份,`Session.hooks` 暴露,`TaskToolDeps.hooks` 透传),扩展自己决定要不要区别对待。失败策略按钩子性质定,不是一刀切:`tool_call` **失败即否决**(它是做拦截的扩展的落脚点——没有权限系统之后这是唯一的卡口,抛错的处理器若被当成放行,拦截扩展一有 bug 工具就全部裸跑;否决消息点名钩子),`tool_result` / `before_agent_start` 失败保留原值,通知型钩子只上报;所有失败经 `onError` 变成 `notice.hookFailed`,绝不冒泡到循环里。**工具包装在 streamText 边界、每次开流现包**(`src/agent/hooked-tools.ts`,`Agent.hookedTools`):tools 对象会被就地改键(MCP 连上后并入、skill 重建、view_image 增删),提前包好的副本看不见;没有工具钩子时原对象直达 SDK,零开销(`tests/hooks.test.ts` 锁住这两点)。否决/错误的呈现与工具内部抛 Error 一样:抛 Error → SDK tool-error → `tool-end`(isError)喂回模型,整轮不终结。`before_agent_start` 只改**发出去的** system,`options.systemPrompt` 那份核心组装的原文不动,prepareStep 的换提示词判定仍比对原文。**followUp 与 inject 是两种东西**:`inject` 把消息塞进正在跑的这一轮(引导),`Agent.followUp()` 排一条**新的一轮**(自己的 turn-start / turn-end,进时间线与历史),空闲时立即开跑。`run()` 自己排水整个链条——首轮 + turn_end 钩子期间排进来的每一轮——整个链条内 `isRunning` 为真(两轮之间 controller 为空,由 `chainActive` 撑着),期间提交的消息走 inject 进下一轮,绝不并发起第二个链条,一次 run() 覆盖整条链、渲染层的忙碌状态不中途熄灭。这是 goal.ts 曾踩的坑的解法:bus 的 `turn-end` 在 try 里就发出,handler 里 `run()` 会被重入兜底转成 inject 混进上一轮历史;`turn_end` 钩子则在 runTurn 完全返回(finally 已跑、历史已落盘)之后才跑。两轮之间的 `abort()` 记标记、丢掉整个队列并补发 `aborted`;轮内中断/出错同样丢队列——用户刚停下,agent 绝不自己续跑;`agent_end` 带 `followUpsDropped`,扩展靠它知道自己排的续跑没发生。turn_end 期间注入的引导没有 followUp 可搭时以 `GUIDANCE_ONLY` 单独续跑一次(不发 turn-start,它已作为引导回显过)。**自定义会话记录**:`store.saveCustom(type, data)` / `store.custom(type)` / `SessionStore.readCustom`(`kind: 'custom'`,Pi 的 appendEntry):open 时按顺序收进内存,恢复回放不看,旧版本静默跳过,**分叉整体带过去**(扩展的状态与 state 同属会话),`custom()` 返回深拷贝。

**扩展(`src/core/extension.ts` 是 API 面,`src/extensions/` 是一方扩展)。** 功能从核心搬出去之后只拿 `ExtensionAPI` 与宿主打交道,成员表与 Pi 同名同义(见下方「Pi 对齐层」)。**面上每个成员都由一次真实的拆分逼出来**——命令 handler 只收 `(args, ctx)`,曾经的 `{ raw }` 因为没有一个扩展读它而删掉;`registerShortcut` 随权限系统一起删掉(零注册方)。命令的 `options(path)` 是取值选择器(**每次现取**——分支列表要跑 git,静态快照会过期;`path` 是已经选过的层,返回项标 `expands` 就再开一层、标 `prefill` 就预填输入框,层数不限,esc 逐层退回,某层返回空表则提交已选的层由 handler 自己解释为什么空——见 `/review`)。`setState(key, value)` 是**结构化数据**(TUI 有专门组件按 key 渲染,todo 清单就是这样),`setStatus` 是一行给人看的文字,`publishRuntime` 只给 `/doctor`——三个「对外说话」的成员分工别混。一方扩展静态打包在 `src/extensions/index.ts`,bootstrap 建一份 API 逐个 `setup`;磁盘扩展用同一份 API。命令表、状态行、结构化状态、提问、组件、界面区域、工具画法全是 `Session` 上的同步 getter(`extensionCommands` / `extensionStatus` / `extensionState` / `uiRequests` / `uiCustoms` / `uiSurfaces` / `toolRenderers`),变化统一经 `extensionsChanged` 通知,App 用一个 `extensionsTick` 信号驱动全部 memo。**处理器绝不能在里面做长活**:handler 里 await 几秒的 git 会让 `/` 菜单卡住——`/review` 因此同步返回,收集与 followUp 在后台跑(`tests/review-extension.test.ts` 钉住「返回时 followUp 还没被调用」)。UI **不替扩展拦忙**:忙不忙由扩展按参数自己判(`/goal clear` 正是循环跑着的时候才要用的),`runExtensionCommand`(extension-cmds.ts)只做派发与错误提示;命令菜单顺序 内置 > 扩展 > 技能,同名内置优先(App.tsx 合表)。状态行是 `ExtensionStatusLine`:多个条目拼一行,带 `since` 的条目由 TUI 按秒追加已用时——扩展只报一次起点,不必每秒推一帧;已用时用 `timeline-data.ts` 的 `formatElapsed`(整秒)。**`session_start` 钩子**(reason: startup / new / resume / fork)在历史与状态换好**之后**触发,扩展在这里从 `entries(type)` 恢复自己的状态;`session_shutdown` 在 dispose。**bus 有 `run-end`**:一次 run() 的整个链条结束(无论结局)。渲染层的空闲以它为准——timeline-controller 在 `turn-end` **不 endWork**,而是把 work 退回 `thinking` 等 run-end;按 turn-end 熄灯会让扩展的自动续跑每两轮闪一次"已空闲"。扩展自己的测试用 `recordingExtensionApi()`(tests/support/extension-api.ts):钩子/工具/命令/状态/提示/custom 记录都落进可断言的容器;`fakeExtensionApi` 必须列全 API 的每个成员。UI 测试的假 session 必须带 `stubExtensions()`(tests/support/extensions.ts):App 挂载即订阅 `extensionsChanged`、调 `attachUi`、读 `uiRequests` / `uiCustoms` / `uiSurfaces` / `toolRenderers`,少任何一个运行期直接炸(`commandOptions`、`uiRequests` 都炸过),刻意不用可选链掩盖。

**这一层踩过的八个坑(code review 抓出来的,都别回退)**:①`registerShortcut` 必须挡 `RESERVED_SHORTCUTS`(App 的 ctrl+c/t/o/r **加上 Input 的 readline 绑定 ctrl+a/e/u/k/w/v/j**——那是两个独立的键盘订阅者,不列进来扩展注册 ctrl+a 会与「跳到行首」同时触发;常量在 extension-types.ts,注册即抛错),**且** App 的扩展派发要排在全部内置分支**之后**——两道都要:光靠顺序,注册了 ctrl+c 的扩展会让用户以为自己的键坏了;光靠拒绝,一个绕过闸门的键仍能吃掉「双 ctrl+c 退出」(`tests/support/otui.tsx` 因此要传 `exitOnCtrlC: false`,与 kit 的 render 对齐,否则上游按 ctrl+c 直接销毁渲染器、这条根本测不到)。②每个扩展的 ctx **不能用 `{ ...extensionContext }`**:`hasUI` 是 getter,展开会在建 API 那一刻(bootstrap 期、attachUi 之前)求值成 false 钉死。③那份 per-extension ctx 必须一路传到**处理器**手上——钩子(`hooks.on` 的第三个参数)、命令(存进 `extensionCommands` 的条目)、快捷键(存进 shortcuts 的条目)、Pi 形状工具的 execute;否则 `ctx.ui.setWidget` 记不进 `Registrations`,`/reload` 留下撤不掉的幽灵 widget。④`waitForIdle` **不能靠 bus 事件等压缩**:`doCompact` 有三条不发 `compaction` 的正常出路(扩展否决、`removedMessages === 0`、历史换代),等事件会永远挂住——真正的实现是 `Agent.whenIdle()`,直接 await `compactionInFlight` 再回头复查(循环:两种状态会互相触发)。⑤`isIdle()` 与 `waitForIdle()` 必须同判据(都含 isCompacting),否则 `if (ctx.isIdle()) sendMessage(...)` 会在压缩窗口里放行。⑥`Agent.sendMessage` 的空闲路径要先 await `compactionInFlight`(与 runTurn 开轮前同一条理由:压缩完成时整体替换 `this.messages`,先 push 的消息被无声覆盖)。⑦`input` 钩子在 `run()` 里**先跑且只跑一次**,转注入时带 `hookApplied` 给 inject——否则 inject 输给它文档里那个竞态返回 false 时,run 会拿原文再跑一遍钩子,改写作废、带副作用的处理器双触发。⑧`toolRenderers`/`messageRenderers` 必须**换引用**(见上一段):就地改则 TUI 的信号永不通知,每读一份新副本则每次 `extensionsChanged` 都白唤醒整条时间线;`jitiByGeneration` 每次新代数要清掉旧代数,否则每 `/reload` 一次泄漏一份 zod/ai 的模块注册表。刻意没有的(docs 的「与 Pi 的差异」里有):会话树、`registerProvider`、`project_trust`、`registerEntryRenderer`/`registerMarkdownTransformer`。

第一个搬出去的是 **`/goal`(`src/extensions/goal/`)**,它也是钩子层的验收:`turn_end` 里评估、`followUp` 续跑,`agent_end` 的 `aborted` 接住两轮之间的 esc,`turn_start` 让恢复来的目标在真正开跑时才重置统计。核心里不再有"目标"的概念:goal-* 四种事件、`GoalController`、`SessionState.goal`、`goalRun` / `goalSet` / `goalClear` / `goalSteer` 四个 Session 方法、`StatusLine` 的 `evaluating` 阶段全部退役。状态存 custom 记录 `type: 'goal'`(`{ condition }` 或 `null` 表示已解除,取最后一条;旧会话 `state.goal` 不迁移)。两处有意的语义变化:评估窗口里用户的消息不再"取代评估器的指令",而是作为轮内引导随下一轮一起喂给模型(链条期间 isRunning 恒真,提交自然走 inject);启动时恢复的目标只靠状态行「目标待续」提醒,不再伪造一条没人听见的 notice。`goal-extension.test.ts` 跑的是**真实的 Agent 链条**(mock streamText/generateText)加一个内存实现的 ExtensionAPI,不是假 agent。

**`/review`(`src/extensions/review/`)是多级选择器的来由,也是「拆到哪里为止」这条线的落点。** 它只是「组一段提示词、跑一轮」——`api.followUp` 就够,所以能整块搬出去:命令、四个预设、base/commit 的第二级取值、失败原因的文案表全在扩展里。收集器(`collectReviewTargets` / `collectReviewCommits` / `collectReviewSummary` / `scopeBlock`)留在 `src/agent/review.ts`,因为 `/simplify` 共用它们——与 `src/lsp/` / `src/mcp/` 同样的分工:机制在核心,策略在扩展。三处有意的语义:①「收集摘要的窗口里用户提交了消息」不需要闸门——`followUp` 会排在用户那一轮**之后**作为新的一轮,而不是被重入兜底转成轮内引导混进用户的提问里(闸门只剩 `/simplify` 在用);② 运行中打 `/review` 不被拒,而是排队等这条链结束(UI 不替扩展拦忙);③ 第二级选择器的标题是 `选择审查预设 ▸ base` 这样的面包屑。

**`/simplify` 与 `task` 明确留在核心,拆分到此为止**——这是查过五家竞品之后的决定,不是没拆完的债。pi / opencode / Claude Code / Codex / Cline **没有一家**在 extension/plugin API 上挂 `spawnSubagent()`:定义永远是声明式文件(`.claude/agents/*.md`、`.codex/agents/*.toml`、opencode 的 `agent` 段),发起永远是宿主内建的、模型可调用的工具(`task` / `Agent` / `spawn_agent` / `use_subagents`),Codex 甚至明写拒绝 —— 它解析了 Claude Code 的 hook schema 却把 `agent` 型 handler「parsed but skipped」。pi 连核心里都不做子代理,唯一的实现是个 example extension,用 `spawn()` 起 `pi -p` 子进程,代价是 frontmatter 解析、user/project scope、信任确认全得扩展自己重写一遍。我们现在的形状(`task` 是宿主内建工具、`runTaskSubagent` 在三个消费方之间 deps-injected)**已经就是行业默认**,那是收敛点而不是债。`/simplify` 要编排四个并行 explore 子代理、合成工具事件、给失败的轴留位置——那是宿主编排,不是策略。真正与竞品有差距的地方在别处:我们的 `TaskMode` 是写死的 `'general' | 'explore'` 两档,模型与步数都不能按 agent 定,而五家的 agent 定义字段高度趋同(身份 + 系统提示词 + 模型 + 推理档位 + 工具/权限范围 + 步数上限)。要在子代理上投入,该投的是声明式 agent 定义,不是扩展 API。

- `src/config/` — layered config: builtin defaults → `~/.mojocode/config.json` → `<root>/.mojocode/config.json` → `MOJOCODE_*` env vars → CLI flags. `providers.<id>.models` is a per-provider model list (`{id, label?, contextWindow?, maxOutputTokens?}[]`, written by hand in the config — the GUI that used to maintain it is gone); `resolveProvider` prefers a matching entry's `contextWindow` (normalized-id match) over the provider-level `contextWindow`, and resolves the entry's `maxOutputTokens` onto `ResolvedProvider` (optional field), which the agent loop passes straight to `streamText`. A model entry's `reasoning` field takes two shapes: an effort string (per-model default effort, beats `providers.<id>.reasoningEffort` and the global default, still translated by `reasoningMapping` and still adjustable via /think) or a **custom params object** — resolved onto `ResolvedProvider.reasoningParams` and merged verbatim into `providerOptions` under the provider key, fully REPLACING the effort mapping (for thinking knobs the family table can't express: Qwen `enable_thinking`, vLLM `chat_template_kwargs`, gateway `reasoning: {...}`). With custom params, effort presets and /think are dead for that model (the deepseek dedicated SDK only passes its canonical keys through, so arbitrary custom params silently drop there). **Which levels are selectable comes from `src/model/catalog.ts`** — a pruned, disk-cached (`~/.mojocode/cache/models-dev.json`, 24h TTL, stale-on-failure, 5min retry backoff) mirror of models.dev's per-model `reasoning_options`/`limit`, surfaced as the `modelCapabilities(providerId, modelId)` Session method. 'auto' (send no thinking params — the untouched default) is NOT a listed level anywhere by user decision: `effortChoices` excludes it, the TUI /think picker filters it, and a bare `/think auto` remains accepted as the only way back to send-nothing. Consumer: the TUI /think picker + validation; everywhere the catalog misses (custom local endpoints, offline first run) falls back to `supportedEfforts`' family table — the catalog provides *which levels exist*, `reasoningMapping` still owns *how to encode them on the wire*. That reconciliation happens in **one** place, `effectiveEfforts` (reasoning.ts), called by bootstrap's `modelCapabilities` so the UI renders a ready-made list. Two traps it exists to close. `effortChoices` is **tri-state** and collapsing it loses thinking control entirely: `[]` means the catalog says the model does not reason, a non-empty array is the catalog's ladder, and `undefined` means the catalog knows it reasons but never described the shape — a *gap*, not an absence, and the majority case upstream (~1400 entries incl. `deepseek-reasoner` and `kimi-for-coding`), so it must fall back to the family table; `??` does that for `undefined` and, crucially, not for `[]`. And catalog levels are intersected with what the wire can actually carry: `unsupported` levels are dropped (kimi k3's `off` is listed by the catalog but `reasoningMapping` emits nothing for it, so picking it left thinking on), while `coarse` ones are kept (GLM-4-class toggle-only models: a level at least means "thinking on"). `effectiveEfforts` also strips `auto` on the fallback path, since the family table counts it as supported. GLM-5+ models (`isGlmEffortModel`) send a real `reasoning_effort` alongside `thinking:{enabled}` — verified against the live Coding Plan endpoint: an invalid value 400s listing `none…max`, and low vs max measurably changes reasoning tokens (0 vs 44); GLM-4 stays toggle-only. Don't regress this to "GLM only has a switch". Preset ids map to models.dev ids via `PRESET_CATALOG_IDS`; unmapped providers fall back to a whole-catalog model-id match preferring reasoning-rich entries. Config writes from the TUI go through `config/save.ts` (`saveApiKey` / `saveProviderChoice` / `saveModelChoice` / `saveCustomProvider` / `saveLanguage` / `saveStatusBar`, all merge-by-key into the global file). Zod schemas in `schema.ts`; provider presets (baseURL, key env vars, default models) in `providers.ts`; web-search backend presets (GLM standalone search endpoint / Exa / custom) in `search.ts` — `resolveSearchBackend` returns `undefined` on a missing key (never `MissingKeyError`, which would trigger the auth wizard) so `web_search` degrades to "not registered". **zod 4 layer trap**: `.partial()` does NOT strip `.default()` — a layer file's *missing* keys come back filled with phantom defaults (`provider:'deepseek'`, `language:'auto'`, …), and since layers merge by priority, a project layer's mere *existence* (e.g. one written by `mojocode install --local`) silently reset every global-layer default-carrier on every startup (the "switched model reverts after restart" bug). Two defenses, both load-bearing: `partialConfigSchema` is hand-written all-optional (new defaulted fields in `configSchema` MUST be mirrored there), and `readLayer` filters parsed output down to the keys actually written in the file.

Web tools live in the `web` extension (`src/extensions/web/`).

That hook is the canonical `tool_result` example: it re-reads the just-written file **from disk** (`write`'s input carries `content` but `edit`'s does not — one path for both, and it's what actually landed), skips `changed: false` (write's unchanged short-circuit never wrote anything) and `isError`, and adds **no field at all** when clean, so the result JSON stays byte-identical to a no-LSP run. Runtime statuses reach doctor through `ExtensionAPI.publishRuntime('lsp', …)` (`Session.lsp` and `ToolContext.lsp` are gone): `undefined` means "this session checked nothing", which is not "no server came up" — doctor then probes for itself. Servers (typescript-language-server / pyright / gopls / rust-analyzer + user-configured) are spawned lazily per language, matched by extension; a server that fails to spawn is remembered as dead for the session. Everything degrades silently to `undefined` — diagnostics must never break the write itself. An empty first diagnostics batch gets a per-server grace window (`emptyGraceMs`, config `graceMs`; rust-analyzer/gopls publish empty-then-real) before being trusted; publishes for *other previously-checked files* arriving during a check surface as `otherFiles` lines (edit A broke B). Config lives under `lsp` (`enabled` / `timeoutMs` / `servers`), with a bare-optional layer schema and per-server-id deep merge in `mergeLayers` (same pitfall as `search`: `.partial()` does not strip inner defaults). Doctor's LSP section does a real initialize handshake for found-on-PATH servers (spawn → init → kill; the TUI passes the extension's published statuses to skip re-spawning).

Mid-turn guidance messages are queued and injected at step boundaries. `init.ts` holds `/init`; `review.ts` is now the **collector library** shared by `/review` (the extension, `src/extensions/review/`) and `/simplify` — the review prompt itself moved to `src/extensions/review/prompt.ts`. It collects its git summary server-side (execa, `reject: false`) and embeds **only scope summaries plus directly runnable commands** — the server resolves `git merge-base` into a SHA itself so the scope block is self-contained, which is load-bearing because that same block goes to `/simplify`'s explore subagents and those have no shell at all; the full diff is never embedded (it would bloat the persisted history and tool output already truncates at 20k). The review prompt is dispatched through `wrapSkillPrompt`, so replay/rewind show `/review <scope>` with zero replay.ts changes; failures are reason codes (`ReviewFailure`) mapped to localized notices — for `/review` inside the extension (it runs in the session process, so it notifies directly), for `/simplify` still in the UI via `SIMPLIFY_FAILURE_NOTICES` (each command exhaustively owns its own column; a shared two-column table does not survive one of them being extracted). git-error carries only the first stderr line (truncated) as `{message}`, never the full blob. `simplify.ts` is `/simplify`, the two-phase cleanup command: four read-only **explore** subagents run in parallel (one per axis — reuse / simplification / efficiency / abstraction), each with its own context and step budget via `runTaskSubagent`; the main conversation then runs one apply turn that merges the reports, verifies against the working tree and applies fixes uncommitted. `runAxisReviews` holds the phase-1 choreography with the subagent channel deps-injected (bootstrap passes `runTaskSubagent`) and emits **synthetic `task` tool-start/tool-end per axis** — `task-progress` only renders on an in-flight task row (`App`'s `activeTools`), and a canned launch makes no real tool call, so without the synthetic events phase 1 is minutes of silence. Axis prompts are honest about explore having **no shell**: the scope block's git commands belong to the apply turn; the subagents work from the summary plus reading files. The whole launch window (git collection + phase 1, during which the *main* agent is idle and `isRunning` is false) is guarded by `cannedLaunchPending` on both input paths — `/simplify` is its only remaining user, since `/review` reaches the same safety through `followUp` (a message submitted mid-collection just gets its own turn first) — esc is ignored, plain messages in `handleSubmit` are rejected: there is no running turn to inject into, and letting one start would make the apply prompt hit the loop's re-entrancy guard and land in the user's turn as a guidance message. Failed axes keep their section ("NOT covered") and an all-fail still runs the apply turn; `/resume` does not replay the phase-1 synthetic rows (they are bus events, not history).

## Gotchas (do not regress)

- GLM's baseURL is `/api/paas/v4` — never append `/v1` (404s).
- Never hardcode model IDs; presets are only starting defaults, `mojocode models` fetches the live list.
- Use `result.responseMessages` for history, not `result.response.messages` — the latter only contains the last step and silently drops earlier tool calls.
- Kit's `render()` defaults `exitOnCtrlC: false` — the renderer would otherwise destroy itself before `useInput` sees ctrl+c, breaking the double-ctrl+c-to-exit logic (startup wizard/picker opt back in).
- Cross-compiling needs the target's `@opentui/core-<platform>` package on disk; `build-binaries.ts` installs missing ones on demand (`npm install --no-save --force`). Do NOT pin them in package.json — each declares os/cpu, so a bare `npm ci` would EBADPLATFORM on every machine. The script also pins `process.env.OPENTUI_LIBC` per Linux target via define — without it both glibc and musl native libs get embedded (+~18MB).
- In-turn compaction only shrinks the messages sent to the model; the persistent history stays long, and the `historyNeedsCompact` flag forces compaction at the next turn start (otherwise the shrunken `lastInputTokens` masks the need). The same flag also covers the *other* blind spot: `setHistory` (resume, rewind) invalidates `lastInputTokens`, and `shouldCompact(undefined, …)` is `false`, so the swapped-in history would go out verbatim. Since **resume no longer switches back to the session's recorded provider/model** (it keeps whatever the current config resolves — ``resumeOverrides` is gone), a long history can land on a smaller window and 400 on the first turn, identically on every retry. `setHistory` therefore seeds the flag from `estimateTokens` (CJK ≈ 1 token, else ¼, images stripped) — a local estimate used **only to trigger** compaction, never to conclude none is needed: under-estimating falls back to the old behavior, over-estimating costs one extra summary. `meta.provider`/`meta.model` are now display-only (session picker, `mojocode sessions`) and are kept current via `store.setModel` on switch/resume.
- `src/config/paths.ts` resolves the home dir from `$HOME`/`$USERPROFILE` first, **never bare `os.homedir()`** — Bun snapshots the home dir at startup and ignores later `process.env.HOME` mutations, so the single binary would put `~/.mojocode` somewhere else than the Node build whenever HOME is set explicitly (containers/CI), and tests that mock HOME silently read the developer's real config instead.
- Node floor is **22**, not 20: execa 10 calls `Set.prototype.union` (ES2024) at import time, so Node 20 dies before `--version` prints. `engines`, the CI matrix and the README all say 22 — keep them in sync if a dependency raises the floor again.
- `vitest.config.ts` (core lane) carries the same `zod` → `index.cjs` and `solid-js` → `dist/solid.js` aliases as the UI config: CI also runs the core suite under Bun (`bun --bun x vitest run`) to guard dual-runtime compat, and without the aliases `import { z }` is undefined there.
